| 正式production | 真实用户数据；与staging网络/权限隔离 | 只读/可逆冒烟；专属测试租户内获准动作，禁止默认破坏性压测 |

## 3. 逐包流程与门禁
~~~mermaid
flowchart LR
 A[冻结任务契约与所有权] --> B[开发者实现及自测]
 B --> C[负责人独立主审]
 C --> D[负责人主线集成与受影响回归]
 D --> E[部署staging精确版本]
 E --> F[独立Agent点击E2E]
 F -->|失败| G[负责人分诊派修]
 G --> B
 F -->|通过| H[冻结同一应用产物]
 H --> I[按授权发布正式]
 I --> J[生产冒烟及监控]
 J -->|严重故障| K[止损/恢复或回滚]
~~~
1. 领取前记录base、文件归属、依赖版本、输入输出和验收ID；先交DSH复用矩阵，主审确认缺口后才自研。
2. 开发者在独占范围实现；单元/接口/真实SDK与本包关键用户流程自测，提交命令结果和未联测项。依赖模拟明确标记，不能因此结项。
3. 主审看代码和独立反例；集成阶段负责人修改server/runner/public/迁移/profile/依赖并核对权限、预算、持久化和恢复。
4. staging使用绑定应用归档SHA、配置版本、迁移版本的候选；测试Agent按完整可执行用例模拟点击，不用直接调接口代替全部用户动作。新增功能深测+核心累计回归+受影响负向场景；另有纯API/故障测试。
5. 两条测试轨：确定性传输保证UI/状态可重复；真实PT证明模型/工具/结果可用。各自报告，付费次数/任务预算提前授权；缺真实证据的功能不能标真实验收通过。
6. 测试通过后发布相同应用归档，env允许不同但差异受审计；任何代码/依赖改变返回staging重验受影响范围，不能“测完再改一行”直接上线。
7. 正式验证检查版本/配置/迁移、登录和关键入口，专属租户内做获准业务冒烟。生产冒烟不能替代staging全量E2E；现有真实用户不参与故障注入。
8. 每包同步台账：分配/开发/主审/集成/本地/staging E2E/上线/生产验证。原七阶段兼容扩展E2E细分；每阶段单独证据，不适用需理由。

## 4. 测试Agent交付格式
test_run_id、时间/环境URL、应用SHA/配置/迁移/用例版本、匿名账号角色、fixture SHA、用例ID、前置、逐步动作、预期/实际、PASS/FAIL/BLOCKED、脱敏截图/trace/控制台与网络错误、Run/产物引用、清理结果、真实PT或替身。禁止把BLOCKED计PASS，不承诺浏览器零错误而忽略favicon等已知问题。
E2E入口/目录需与Gemini协调；在所有权变更前只交测试用例和接入建议，不读改tests/e2e/。工具选型优先仓库既有浏览器设施和可复跑脚本，不为测试新建平行框架。

## 5. 缺陷分诊与修复
所有测试失败进入统一缺陷表，负责人先分诊，测试Agent可建议归属但不自行定责。字段：BUG-ID、包/AC-ID、版本/环境、严重度、复现/期望/实际、脱敏证据、责任人、状态、修复commit、复测运行。状态为New→Triaged→Assigned→Fixed→Retest→Closed；失败重开，Duplicate/Deferred有依据。
| 严重度 | 例子 | 处理 |
|---|---|---|
| S0 | 越权/泄密、不可控付费、数据破坏 | 停止扩大使用、负责人立即止损；可回滚范围按已审方案；缺陷修复后独立复测 |
| S1 | 新核心流程不可用、错误结果被当成功、无法恢复关键数据 | 阻止该版本放行；已上线先禁用受影响能力或修复 |
| S2 | 可绕过的功能问题 | 记录用户影响与修复计划，是否放行由负责人明确接受 |
| S3 | 文案/低影响视觉 | 排期处理，不与业务失败混淆 |
包内实现→原作者修复；共享接线/架构→负责人；测试代码错误→测试负责人/Agent；PT/资源→负责人整理外部依赖。每次修复加防回归，原作者自测后由独立Agent复测。跨包问题不让程序员互相猜责任。

## 6. 开始条件与终局标准
示范包用户确认后，再逐包补齐尚未完整扩写的任务包，逐包给可执行需求而非复制通用段落。当前09/10样本已通过；其余范围剔除Gemini已完成的01–08后为11–35共25包，规格已扩写，见[分类与决策索引](PACKAGE-SPEC-INDEX-20261104.md)，不覆盖原候选。上线授权不由任务包本身产生；已有授权只在原范围有效。尚未建好staging时可推进开发和本地主审，staging E2E标BLOCKED，不伪称环境已建或测试Agent已执行。
最终每个适用包：需求逐条可追溯→DSH复用→独立主审→主线集成→本地门禁→staging点击E2E和真实PT适用证据→正式版本/冒烟→历史恢复/权限反例→缺陷关闭。功能被延期则保留未完成，不通过改名字交付。

## 7. 用户端分支逻辑的任务包深度标准
涉及用户操作流程的每包，必须在契约之外自行走完整旅程，交决策树、分步详解表与节点→AC验收映射。深度样本：[09文件编辑第7节](REFACTOR-FILEEDIT-PACKAGE-20261103.md#7-ui与可观察行为)与[10 Seedance第2–4节](REFACTOR-SEEDANCE-PACKAGE-20261103.md#2-用户旅程与决策树)。09/10样本已获用户通过；剩余25包的新增建议/阈值/范围选择仍按包内决策表分别确认，不能把样本通过当作后续所有产品决定已定。

| 必答问题 | 文档要求 |
|---|---|
| 用户从哪来、默认看到什么 | 入口、前置身份/权限、默认来源和排序、空态/加载/禁用原因；优先已有资源，何时才进入上传等兜底写清 |
| 每个选择会去哪 | 主路径、返回/修改/放弃、模式切换、外部跳转后返回、角色或多输入组合；不能用一句“复用XX”跳过 |
| 每种异常如何恢复 | 区分空/失败/未知、前置拒绝/提交后未知、取消请求/真实终态；给具体界面、动作与禁止行为，避免重复写入或付费 |
| 离开后还能否继续 | 刷新、历史重开、草稿、双标签/并发、权限失效、资源过期及下载；哪些持久、哪些仅会话内明确说明 |
| 哪些事实与决策尚未确定 | 每个“待确认”给建议、理由/代价、用户决策或外部证据责任、未确认时安全边界；不写成现有能力 |
| 如何验证覆盖完整 | 每一分支有节点、可观察预期与AC/测试层；键盘/焦点/错误恢复也入表。交付前人工逐分支走查，不能只测成功路径 |

“所有分支”指本包承诺范围内可达的用户状态与风险分支，不机械枚举无意义组合；需要合并等价分支时写依据，权限、付费、数据变更及外部未知状态不得省略。DSH复用矩阵回答实现来源，用户旅程回答产品行为，两者均为主审输入。正文与验收只在所属任务包维护；独立讨论稿合并后保留迁移入口，不保留第二份可独立更新的流程。
