# T03 · Ambiguous chat POST recovery by idempotent retry (2026-10-22)

**Slice: local PASS; T03 remains incomplete.** When the browser's initial `POST /api/chat` rejects before response headers arrive, the server may already have durably admitted the Run. `runChat` now makes one retry with the exact same `Idempotency-Key` and serialized body. This lets the existing server replay path return/attach to the original Run; it does not generate a fresh key or create a second model execution. The existing refresh path remains GET-only when a Run ID is known.

Evidence: `node --test tests/regression/ui-run-resume-review-test.mjs` passed 22/22. The added regression simulates the first response being lost after one durable admission and asserts two transport attempts use identical key/body. `node --test tests/regression/task-execution-test.mjs tests/regression/task-store-test.mjs` passed 2/2; `task-execution-test.mjs` confirms a repeated same-key submission returns the same Run and executes once. No provider/model call was made; browser retry was exercised with a fixture.

Limits: the automatic retry is bounded to one and only handles a rejected fetch before a response object exists; HTTP responses and SSE disconnections use their existing paths. If both attempts fail before the browser receives `X-Agent-Run-Id`, it still cannot persistently resume that Run after a page reload; durable client submission-key storage/recovery remains open. This evidence does not establish real browser/provider behavior, production retry accounting, or the remaining T03 acceptance criteria.
