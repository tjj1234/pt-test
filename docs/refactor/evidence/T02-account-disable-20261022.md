# T02 · Trusted account disable gate (2026-10-22)

**Local slice: PASS; T02 and AC01 remain incomplete.** V2.0 requires product-side account disable and local session revocation. Added nullable `users.disabled_at` via migration 019 and a trusted server-side `auth.setAccountDisabled(userId, disabled)` capability. Disabling records the timestamp and revokes all persisted sessions in one transaction; session lookup rejects disabled accounts, and Google callback refuses to mint another session for a disabled bound identity. Re-enabling clears the marker and allows a later Google sign-in. There is deliberately no public HTTP route for this capability.

Regression evidence: `node --test tests/regression/google-auth-test.mjs tests/regression/google-auth-review-test.mjs tests/regression/google-session-upgrade-test.mjs tests/regression/storage-upgrade-test.mjs` passed **25/25** with real isolated PGlite. The new case verifies an active Google session, disable/revocation, rejected callback, re-enable and new session. The storage-upgrade test applies migration 019 to a legacy fixture, checks existing users remain enabled and assets/session policy remain intact, then reruns migrations idempotently. No real account, Google endpoint, key or provider was accessed.

Limits/next dependency: the capability is callable only by trusted server-side operators; no admin UI or authenticated operator HTTP workflow has been defined or exposed. Production Google/OAuth, target HTTPS, real PostgreSQL and operational account-disable runbook remain unverified. T01 retains its real PostgreSQL/packaging evidence gaps. AC01 still requires a real first-use chain through Google sign-in, BYOK, default AUTO and a real question; this test is not AC01 evidence.
