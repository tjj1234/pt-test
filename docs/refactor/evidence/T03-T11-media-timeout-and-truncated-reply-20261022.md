## Media submission and 120-second guard

`business/media/powertokens.cjs` uses a 120-second default image polling guard after a successful submission returns `task_id`; the POST has its own 180-second request abort signal. The polling guard is not a PT-side generation deadline. `media-run-handler.cjs` durably records intent before POST and the observed task ID before polling. When polling times out with a known task ID, this handler does not issue a second POST; the external-operation recovery worker can later query the known task through a GET-only adapter.

The deduplication key is `runId:requestId`, not a hash of prompt/arguments. A new user Run or a model retry using a new tool request ID is a distinct external operation and may submit another POST. Therefore the code proves “one POST per handler operation after a known task ID timeout,” but does not prove how many submissions or charges occurred for the screenshot’s three separate messages.

An isolated PGlite/fake-transport test, `tests/regression/t03-media-timeout-no-resubmit-test.mjs`, verifies durable intent/task ID, accepted state after local timeout, exactly one POST, and query-only recovery to succeeded with POST count still one. It makes no external request and does not prove PT billing, target-host behavior, or whether a live model initiates a second tool call.
