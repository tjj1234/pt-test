**版本：** v1.0（供11/4会议使用）
**面向：** PT 产品/网关/模型接入/账单/基础设施团队

**说明：** 下文按「现有接口，需要补充的字段/参数」和「新增接口，需要开发」两部分列出。标"（建议）"的路径/字段为我方建议方案，最终以PT实际能力为准；请逐条回复：已支持 / 需配置 / 需开发 / 有替代方案 / 不支持，并尽量给出对应端点、参数名、限制条件。

## 第一部分：现有接口，需要补充

### 1. 资产库签署状态查询

- **现状：** `GET /v1/asset/agreement/status`，已可用。
- **需要确认（无需新增字段）：** 请确认签署状态确实只有两态——`agreement_accepted` 为布尔值，没有有效期/到期/续签字段；`asset_library_enabled` 是独立的资产库启用状态，与协议签署状态分开，不会新增协议 scope/revision 之类的门禁字段。

### 2. 消费记录查询

- **现状：** `GET /v1/logs/query`，当前返回单条 `data`，无查询参数。
- **需要新增的请求参数：**

| 参数名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| start_time | string | 否 | 查询起始时间，UTC，左闭 |
| end_time | string | 否 | 查询结束时间，UTC，右开 |
| key_id | string | 否 | 按Key过滤 |
| request_id | string | 否 | 按单次请求ID过滤 |
| task_id | string | 否 | 按异步任务ID过滤 |
| client_operation_id | string | 否 | 按我方传入的逻辑操作ID过滤 |
| model_id | string | 否 | 按模型过滤 |
| status | string | 否 | 按消费状态过滤 |
| cursor | string | 否 | 分页游标（opaque） |
| limit | integer | 否 | 单页条数，默认/最大值由PT给出 |

- **需要的响应结构变化：** `data` 由单条对象改为列表+分页信封：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| items | array | 消费记录列表，单条结构沿用现有字段 |
| next_cursor | string\|null | 下一页游标 |
| has_more | boolean | 是否还有下一页 |
| data_as_of | string | 本次查询的数据快照时间 |

- **需要确认：** 若直接改动会破坏现有单条调用方，是否可以另开一个版本化路径（如 `/v2/logs/query`）保持旧接口兼容；分页排序建议固定为 `(consume_time, consume_id)`，避免迟到记录/同秒多条导致漏记或重复；退款/冲正希望以新的调整记录体现并关联原 `consume_id`，而不是直接修改原记录。
- **需要新增字段：** 每条记录补充 `client_operation_id`（关联我方逻辑操作）、`billing_state`（`pending`/`finalized`/`refunded`/`adjusted`/`unknown`，失败也可能产生费用）。

### 3. 余额查询（按Key粒度）

- **现状：** `GET /v1/billing/balance`，已可用，返回按Key余额。
- **需要确认/补充：**
  - 登录令牌下如果对应多个Key，当前是如何选择"确切Key"的？是否需要新增 `key_id` 查询参数来指定？
  - 账号余额与Key配额之间的关系（是否Key共享账号余额，还是Key有独立额度）。
  - `key_id` 字段目前是掩码字符串，如果不能唯一稳定标识一个Key，是否可以新增一个不敏感的 opaque Key ID 字段。

### 4. 账单查询（按模型类型汇总）

- **现状：** `GET /v1/billing/usage`，支持 `start_date`/`end_date`，按模型类型汇总。
- **需要新增的请求参数：**

| 参数名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| key_id | string | 否 | 按Key过滤汇总范围 |

- **需要确认/补充：**
  - `data_as_of` 对应的时区，以及 `period_start`/`period_end` 是否为闭区间，需要明确说明。
  - 当前统计是否存在结算延迟水位（即最近一段时间的消费可能还未计入汇总），如果有，需要一个字段标明"已结算到哪个时间点"。
  - 汇总口径需要和第2条消费明细口径一致，以便我方做对账；如有后续冲正，需要说明如何体现在汇总数字里。

## 第二部分：全局性要求（适用于所有接口，不是单独的接口）

### 5. 认证与身份隔离

- 请说明每个接口接受的凭据类型（BYOK API Key / 平台登录token / 短期令牌），格式是否为 `Bearer`，各自的 scope、过期时间、撤销和刷新方式。
- Key ID 需要稳定、不敏感、且能唯一对应一个授权范围；如现有掩码字符串做不到唯一标识，建议新增一个 opaque Key ID 字段。
- 需要确认：一个账号/Token 无法通过改写请求里的 `key_id`/`task_id`/`asset_id` 读到另一个账号的资源；一个Token下可访问多个Key时，服务端需要校验每次访问的资源归属，而不是指望调用方自己过滤。
- 建议我方在请求中携带以下头部，供排查和幂等使用：

| 头部/字段 | 含义 |
| --- | --- |
| X-Client-Request-Id | 每次HTTP尝试的唯一标识 |
| client_operation_id | 一次逻辑付费操作的唯一标识（可能对应多次HTTP重试） |
| traceparent | 可选，分布式追踪 |

- 需要PT侧生成并在响应中返回：`request_id`（每次请求）、`task_id`（异步任务）、`consume_id`（扣费记录）。请说明这几个ID的长度上限、保留期、是否可被后续查询检索到。

### 6. 错误与响应格式

- 控制面接口（资产/消费/余额/账单）请保留现有 `code`/`data`/`msg` 外层；新增接口请提供版本化 OpenAPI，明确响应外层结构，不要同一类接口混用不同外层。
- 标准推理兼容端点（chat/images/videos等）不需要额外包一层自定义JSON，以免破坏现有SDK兼容性。
- 所有响应需要能拿到 `request_id`（流式场景下通过响应头或事件流返回）。
- 流式响应如果中途出错，需要有明确的终止状态，不能用正常的 `finish` 事件掩盖失败。
- 错误体建议至少包含：

| 字段 | 说明 |
| --- | --- |
| error_code | 稳定的错误码（不是只有文案） |
| message | 可读信息 |
| request_id | 关联请求 |
| retryable | 是否属于可重试类别（仅表示类别，不代表允许我方自动重新提交付费操作） |
| retry_after_seconds | 适用时给出 |
| operation/task 引用 | 适用时给出 |

- 需要用更细分的状态码区分以下几类当前都归到403的情况：

| HTTP | 需要区分的含义 |
| --- | --- |
| 400/413/415/422 | 参数错误 / 输入过大 / 格式不支持 / 语义或组合不支持 |
| 401 | 凭据无效 |
| 402 | 余额不足 |
| 403 | 权限不足或模型已下架（需要能区分这两种原因） |
| 404/409/410 | 资源不存在 / 幂等冲突或状态冲突 / 已过期（跨账号访问可统一返回404防止枚举） |
| 429/503/5xx | 限流 / 容量暂不可用 / 上游异常（需标明该请求是否可能已经被受理） |

- 对于“客户端收到500或连接中断，不确定任务是否已被受理”的情况，需要能查询到一个明确的 `acceptance_state`（`not_accepted`/`accepted`/`unknown`），而不能把 `unknown` 当成最终失败处理。

### 7. 数值与版本策略

- 计费数值建议提供十进制字符串字段（同时保留现有整数 `credits` 字段用于兼容），并明确精度、舍入规则、单位、价格生效时间。
- 用量/费用未知时字段应为 `null` 或显式 `known=false`，不能用 `0` 代表未知。
- 新增字段请保持向后兼容（只加不减/不改语义）；如有破坏性变更，走独立版本路径并提前通知。

## 第三部分：新增/需补充能力的接口

### 8. 模型能力与资格查询

- **建议：** 扩展现有 `GET /v1/models`，或新增一个独立的能力查询接口（不要求替换现有接口）。
- **需要返回的字段：**

| 字段组 | 字段 |
| --- | --- |
| 身份/版本 | model_id, provider, display_name, model_revision（如可得）, availability, deprecated_at, replacement |
| 支持的任务/端点 | text_chat / image_understanding / image_generation/edit / video_generation / ASR 等，及各自对应的 method+path |
| 输入输出限制 | 支持的模态、MIME类型、最大文件大小/张数/帧数/音视频时长/总大小、上下文及输出token上限、是否支持多轮 |
| 推理/工具能力 | 支持的 reasoning_effort 档位列表、是否支持 tools/tool_choice/并行工具调用、JSON schema 输出能力及限制 |
| 参数schema | 每个参数的必填/默认值/枚举/范围/互斥关系/组合限制 |
| 当前Key资格 | allowed（布尔）、reason_code、quota_scope、requires_agreement、checked_at、可选 eligibility_expires_at（仅资格缓存时间，不是协议有效期）、capability_version |
| 价格引用 | pricing_version、计费维度、价格查询接口引用 |

- **需要确认：** 目录只列出模型事实+当前Key资格两部分，不代表“目录里有=一定能调用成功”；希望权限不足/模型已下架/未知模型这几种情况能在资格字段里逐一区分。

### 9. 对话/工具/推理兼容性确认

- 这不是新接口，是希望对现有的对话类兼容端点（Chat Completions / Responses 等）提供一份书面的逐模型兼容矩阵+真实请求响应示例，覆盖：多轮对话、SSE流式、工具调用（含参数分片和tool-call ID）、tool result续轮、推理强度档位切换、图片字节/URL输入、取消/断线、各类错误。
- **需要的字段行为：**
  - 不支持的参数需要返回明确错误，不能静默丢弃（例如传了 `reasoning_effort` 但模型不支持时，不能默默忽略）。
  - 响应需分别返回 `requested_model`（我方请求的模型）和 `resolved_model`（实际执行的模型）；如果上游不披露实际模型，`resolved_model` 返回 `null`，不要伪造一个值。
  - `usage` 字段需要注明输入/输出/缓存读写/推理token，以及这些是否计费；SSE流被中断时，如果拿不到完整usage，应保持未知状态，不能填0。
  - 结构化JSON输出能力需要按模型声明支持级别，不支持某个schema时需要返回明确错误。

### 10. 异步任务提交/查询/幂等/取消

- **建议：** 适配到现有标准端点（`/v1/images/generations`、`/v1/videos` 等任务型接口），不要求改路径。
- **需要新增的请求能力：** 支持 `Idempotency-Key` 请求头或 `client_operation_id` 字段，鉴权通过后原子占位并绑定请求摘要。
- **需要的行为：**

| 场景 | 期望行为 |
| --- | --- |
| 同账号/Key、相同操作、相同参数重复提交 | 返回原有的task及状态，不新建任务、不重复扣费 |
| 相同操作但参数不同 | 返回 409，错误码如 `IDEMPOTENCY_CONFLICT`，不覆盖原任务 |
| 响应丢失、不确定是否提交成功 | 可以用 `client_operation_id` 查询是否已被受理（只有task_id不够，因为可能连task_id都没拿到） |
| 查询任务状态 | 返回 accepted/queued/running/succeeded/failed/canceled/expired 等状态及合法的状态转换、时间戳、可选进度 |
| 取消任务 | 返回 best_effort/confirmed/not_supported 三态，并单独返回 `billing_state`（取消或超时不代表一定免费） |
| 结果过期/被删除 | 任务状态和"结果是否还能下载"分开表示，已成功的任务不能因为结果过期就显示成"未执行" |

- **需要PT填写：** 幂等保留窗口的具体时长（需要覆盖最大任务耗时+结果未知时的核对窗口）。
- **建议的异步响应字段：** 提交响应至少包含 `task_id`, `request_id`, `client_operation_id`, `status`, `submitted_at`, `billing_state`, `poll_after_seconds`；最终查询再补充 `outputs[]`, `usage`, `cost`/`consume_id` 引用, `completed_at`。
- **Webhook（可选增强，非必需）：** 如果提供，需要验签、时间窗口校验、防重放、稳定的 `event_id`、乱序/重发场景的处理说明；轮询方式需要始终可用，不能只靠webhook。

### 11. 资产上传与引用

- **需要的资产对象字段：**

| 字段 | 说明 |
| --- | --- |
| asset_id | 资产标识 |
| owner scope | 归属范围 |
| MIME | 文件类型 |
| size_bytes | 文件大小 |
| SHA256 | 可提供时给出 |
| processing/status | 处理状态 |
| asset_expires_at | 可选，资产资源本身的有效期（与协议签署状态无关） |
| 可用任务模式 | 该资产能用于哪些任务 |

- **需要确认：** 继续沿用现有协议签署两态（`agreement_accepted` true/false），不新增协议 scope/revision 之类的门禁。
- **上传方式：** 单文件上传优先支持；大文件分片/断点续传可以作为后续增强。
- **远程URL输入（如果支持）：** 需要说明支持的协议、大小限制、是否跟随重定向、授权方式；需要明确拒绝私网地址和带凭据的URL，避免被当作访问旁路。
- **多模态参考资产角色：** 需要显式的角色字段（例如 `first_frame`/`last_frame`/`reference_image`/`reference_audio`），不能靠数组里的位置顺序来猜角色。
- **输出资产字段：** 角色/MIME/大小/尺寸/时长、下载URL或资源ID、下载认证方式、可选SHA、可选有效期。
- **需要确认：** 结果URL目前长期有效这一点能否保持；删除/撤销资产的例外情况和允许重试下载的范围。

### 12. 配额与容量查询

- **建议：** 新增一个 limits 查询接口，或首期直接提供书面配额说明。
- **需要的字段：** 按 Key/账号/模型三个粒度的 RPM、TPM、并行推理任务数、媒体任务在途数、日额度、文件/资产容量、计数窗口与重置时间。
- **需要的429响应增强：** 返回命中的是哪个限流维度，并带 `Retry-After`；上游模型本身故障不应该报成"无权限"。
- **需要PT确认的问题：** 5/10/25/50并发混合任务档位分别能提供多大额度、对应价格；排队最长时间；任务结果保留多久；状态查询接口本身是否有独立限流；突发流量的处理策略；扩容的联系方式和周期；模型维护/下架的通知渠道。

### 13. 语音转写 ASR

- **建议端点：** `POST /v1/audio/transcriptions`（对齐业界通用格式）。
- **请求字段：** model, file/asset, language（可选）, timestamps粒度, diarization（可选，说话人分离）。
- **响应字段：** text, segments[start, end, text], language, duration, speaker（可选）, usage/计费引用。
- **需要确认：** `start`/`end` 的单位（建议秒）及其含义（对应原始文件的哪个切片/偏移）；对中文、中英混合、静音片段、损坏文件、超出大小限制、多说话人的处理方式；如果不支持说话人分离，需要明确声明不支持而不是返回空值。

### 14. Seedance 视频生成

- **建议：** 沿用现有已支持的任务型端点，补充精确字段。
- **请求字段：** 精确的 model/revision, mode, prompt, reference assets及其角色, duration/aspect/resolution, 音轨选项。
- **响应字段：** 任务生命周期状态, outputs, 实际生效参数回显, usage/费用引用。
- **需要确认：** 文生/图生/多参考/首尾帧等每种模式的具体支持情况；资产输入协议和各模式的前置条件；不支持的模式需要明确报错，不能静默换成另一个模型。

### 15. 视频理解

- **建议：** 在现有兼容接口基础上扩展。
- **请求字段：** model, video asset 或带时间戳的frames, audio（可选）, question, 采样要求。
- **响应字段：** 回答, 时间引用, 实际处理的区间/采样信息, usage。
- **需要确认：** 是原生视频理解还是基于多帧输入拼接，这个区别需要对外明确；抽帧数量限制、音轨是否被实际理解，都需要说明。

### 16. 语音合成 TTS

- **建议端点：** `POST /v1/audio/speech`（对齐业界通用格式）。
- **请求字段：** model, text, voice, language（可选）, format, speed（给出范围）。
- **响应字段：** 音频字节或task/asset引用, MIME, duration, usage。
- **需要确认：** 流式和非流式分别是否支持；中文文本、空输入、长文本、取消的处理；默认不开放音色克隆能力。

### 17. OCR 文档识别

- **建议：** 新增文档处理任务接口。
- **请求字段：** model, asset, page_range, layout/table 选项。
- **响应字段：** pages[page, text, blocks, bbox, confidence], tables/cells, usage。
- **需要确认：** 页码从0还是从1开始、坐标系定义、置信度取值范围；对中文扫描件多页、旋转、表格、加密文件、空白页的处理；不确定的内容不应该被模型编造填充。

### 18. Embeddings / Rerank

**Embeddings：**
- **建议端点：** `POST /v1/embeddings`（对齐业界通用格式）。
- **请求字段：** model, texts, dimensions（可选）。
- **响应字段：** 按输入顺序的 index/vector, 模型版本/维度, usage。
- **需要确认：** 空文本、超长文本、批量请求、返回维度一致性；模型升级时不能无声改变向量维度或向量空间。

**Rerank：**
- **建议：** 新增端点，路径由PT定。
- **请求字段：** model, query, documents, top_n。
- **响应字段：** 原始index, score及其取值范围/排序方式, usage。
- **需要确认：** 截断策略、文档稳定ID、长度限制；score 不默认等同于概率值。

### 19. 实时语音（优先级较低，可后置）

- 协议细节待PT提供。
- **请求字段（建议）：** model, 音频格式, 语言, turn/VAD配置, 短期受限token。
- **响应字段（建议）：** session/events, partial/final转写或音频, turn ID, usage。
- **需要确认：** 是否可打断；乱序/断线/过期的处理；最终计费方式；短期token不应能调用账户级别的账单接口。

### 20. Computer-use 模型接口（优先级较低，可后置）

- **建议：** 在现有工具调用协议基础上扩展，不要求PT提供操作系统层面的控制权限（本地执行由我方宿主负责）。
- **请求字段（建议）：** model, 截图/屏幕尺寸, 目标描述, 受限动作schema, 可选历史记录。
- **响应字段（建议）：** 结构化action，或"已完成"/"需要确认"状态, 坐标系/目标定位方式, usage。
- **需要确认：** click/type/scroll等每种动作的具体schema；如果没有原生支持，是否有视觉识别+工具调用的组合方案。
