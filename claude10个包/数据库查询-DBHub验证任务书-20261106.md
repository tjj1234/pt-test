# 数据库自然语言查询 × DBHub 验证任务书（给 Codex）

> 定位：P0。这是 DSH/开源能力调研表里唯一一项本身就是真实、可信的候选（Bytebase 出品，不是未经验证的社区占位仓库），可以直接进入验证阶段，不需要先纠正事实前提。

## 一、现状基线（不用重新调研）

北极星当前没有任何"自然语言查询数据库"的通用能力。现有的 `attribution.query`、`ga.query` 是写死的固定业务 API 封装，只能查特定的归因/GA4数据，不是"接上任意数据库、自然语言转查询"的通用工具，两者不是一回事，不要混着算已经有的能力。

## 二、候选：DBHub（bytebase/dbhub）

支持 PostgreSQL、MySQL、MariaDB、SQL Server、Oracle、SQLite。默认只暴露两个工具，支持只读模式、查询超时、结果行数限制。

## 三、前置必答题（不能跳过，没有清楚答案之前不要往下测功能）

北极星是多租户产品，团队已有明确审计结论：DSH 原生自带的通用文件/命令工具因为"沙箱隔离没有通过安全验证"被整体关闭。任何新工具接入前必须先回答：

1. DBHub 连接的数据库凭证是按租户隔离配置的，还是一套共享连接？如果是共享连接，怎么保证租户 A 的自然语言查询不会被模型"顺手"拼出跨租户的 SQL、读到租户 B 的数据？
2. 默认只暴露的那两个工具具体是什么（读 schema？执行只读 query？），这两个工具本身有没有做"只能查当前租户授权范围内的表/行"这层过滤，还是完全依赖后面接的是哪个数据库账号？
3. 查询超时和行数限制是否可配置到北极星需要的粒度（防止一次自然语言查询跑出一个超大结果集或者长时间占用连接）？

## 四、功能验证任务（答完上一节才能做）

1. 用北极星自己的归因/广告数据样例库（脱敏），测试自然语言转查询的准确率——重点测"容易被模型理解错的边界case"（时间范围模糊、多表join、聚合口径不一致），不要只测简单的单表查询。
2. 核实 DBHub 是否原生支持 MCP 协议接入（报告里说支持 stdio/HTTP），实测接入北极星现有的 DSH MCP 客户端（`dsh-mcp-client`，这个是真实存在的 DSH 原生能力，可以直接用）需要多少适配工作。
3. License 原文核实（去仓库 LICENSE 文件确认，不要信转述），确认可商用。
4. 维护活跃度核实：最近一次 release 时间、open issue 数量、是否有安全漏洞历史。

## 五、边界

- 本轮只做验证，不接入生产环境，不给任何租户开放真实数据库写权限（只测只读）。
- 不需要给"最终选型建议"替团队做决定，只需要把真实能力边界、限制、证据来源说清楚。
