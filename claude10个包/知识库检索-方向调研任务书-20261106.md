# 知识库检索 × 真实候选调研任务书（给 Codex）

> 定位：P1。上一轮报告把"DSH Memory Knowledge / Qdrant"打包成一项，但这两个不是同一类东西，必须拆开看——而且其中"DSH Memory Knowledge"这个名字本身就落在上次已经证伪的那个第三方插件生态里（同 `dsh-office-*`、`dsh-plugin-browser` 一样的模式：搜一下能找到一串几乎同名同描述、不同账号发的仓库，比如 `menotbobbybrown/dsh-plugin-memory`、`NattoCB/dsh-plugin-memory`、`yoxaass/dsh-plugin-memory`、`yangyongzhen/dsh-memory`），不是经过验证的官方/成熟社区能力，**不要再往"DSH 原生记忆插件"这个方向调研**。

## 一、先把两个东西拆开

- **Qdrant**：真实、成熟的开源向量数据库项目，是一个"你自己拿来建索引"的基础设施组件，不是一个打包好的"知识库技能"。
- **"DSH Memory Knowledge"类插件**：同上一轮 Office/Browser 那批一样质量参差的第三方占位仓库生态，不建议作为候选认真评估。

## 二、现状基线（不用重复建设）

北极星已经有两块跟"知识"相关的真实能力：

1. **长期记忆**：通过 `memory.memoryLines(uid)` 把记忆内容直接拼进系统提示词里，不是 Agent 主动检索、带来源追溯的知识库。
2. **资料检索面板**（`#sourceBtn`，已上线）：用户可以检索已有知识库，勾选的条目作为权威背景注入，回答末尾带引用标号——这已经是一个"带来源的检索"能力，不是从零开始。

另外 WB能力对照文档里提到"包30（记忆管理中心）"还在 V1 规格阶段，没有做完。

**这项任务真正要回答的是**：现有的"长期记忆 + 资料检索面板 + 包30规划"这套东西，跟"知识库检索"这个需求之间还差什么，而不是去找一个外部插件整个替换掉现在这套。

## 三、给 Codex 的任务

1. 先梳理清楚现有"长期记忆"和"资料检索面板"分别覆盖了什么、包30规划里还打算补什么——避免调研出来的东西跟已经在规划里的东西重复。
2. 如果梳理下来确实有缺口（比如"检索召回的准确率不够""没有向量语义检索、只能靠关键词"），再去评估自建一套基于 Qdrant 的语义检索层的工作量和架构影响,**不要去调研/安装任何"DSH Memory Knowledge"类第三方插件**。
3. 多租户隔离必答项：如果自建向量索引，索引和检索范围必须按租户严格分区，不同租户的知识不能互相检索到——这个设计要写清楚，不是等出问题再补。

## 四、边界

- 不装、不深入评估任何 `dsh-plugin-memory*`、`dsh-memory*` 类第三方仓库。
- 不要在没搞清楚包30规划范围之前就去外部找替代方案，容易做出跟已有规划冲突或重复的东西。

## 五、交付物

一段简短结论：现有能力 vs 包30规划的覆盖盘点 → 是否存在真实缺口 → 如果有，Qdrant 自建方案的架构草案 + 隔离设计 + 工作量评估；如果现有规划已经覆盖，直接说明不需要额外引入。
