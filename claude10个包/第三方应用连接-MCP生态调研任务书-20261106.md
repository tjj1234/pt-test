# 第三方应用连接（更多 MCP Servers） × 调研任务书（给 Codex）

> 定位：P2，而且是这一批里最容易走偏的一项——"按真实需求扩展"这句话本身没有指向任何具体东西，照原样执行很容易变成"随便列一堆 MCP Server 目录"，产出一堆没人要用的清单。这份任务书先把范围收紧。

## 一、先回答一个已经存在、但还没拍板的产品决策

WB能力对照文档里提到：**包25（第三方资料与应用连接，V2）目前还没决定"首个要接的系统"是谁**，路线图原文是"不提前扩大首版承诺"。也就是说，"接哪个外部系统"这件事本身还没有答案——在这个答案出来之前，去调研一长串通用 MCP Server 目录（广告平台/CRM/数据库/各种 SaaS）没有意义，因为调研结果用不上，不知道该针对哪个系统深挖。

**这项任务的第一步，不是调研，是先去确认包25有没有新进展、有没有定下第一个要接的系统。** 如果还没有，这项任务直接停在这一步，不要往下产出一堆通用调研。

## 二、如果包25已经定下了具体系统

针对那一个具体系统（比如如果定的是某个广告平台/CRM），再去做真正聚焦的调研，参照最初调研任务书里"方向3"的要求：

1. 这个系统有没有官方维护的 MCP Server，还是只有社区实现——官方 vs 社区质量差异要讲清楚。
2. 授权范围控制、撤销机制是怎么设计的——用户要能明确看到"给了这个连接器什么权限，能随时撤销"，这是产品侧明确要求的，不是可选项。
3. 多租户隔离必答项：不同租户连接的是各自独立的账号授权，还是有没有可能共享一套凭证导致串数据。

## 三、边界

- 不要在没有具体目标系统之前，泛泛调研"MCP 生态里有哪些连接器"——这种清单没有决策价值。
- 不需要重新论证"要不要用 MCP"——已经确定会用，只是还没排期接哪个。

## 四、交付物

如果包25还没定下系统：一句话结论"目前没有具体目标，这项任务暂时不需要往下做，等产品侧拍板后再启动"。
如果已经定下系统：针对那一个系统的调研报告，按上面三点展开，不要扩大到其他系统。
