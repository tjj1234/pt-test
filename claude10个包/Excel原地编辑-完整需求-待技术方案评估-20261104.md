# Excel原地编辑（增删行+保留格式+保留公式）—— 完整需求，待技术方案评估

> 用途：这份文档描述的是**目标能力**，不是已拍定的实现方案。其中"公式在增删行时如何正确调整引用"这一节，我们还没有满意的方案，希望拿这份文档去评估——包括评估是否有比"直接拒绝整次操作"更好的处理方式。请不要把文档里举的候选方案当成已采纳的答案。
>
> **更新（2026-11-06）**：一、二、三、四、五、七节是原始需求基线，没有改动。新增的**第六节**是对上一轮技术调研（DSH/开源能力）的核实结果和下一步具体验证任务，请从第六节开始看最新进展。

## 一、背景

产品（北极星，一个面向运营团队的Agent）目前只能"读取数据、生成一份全新的Excel文件"，不能"打开一份运营团队已经在用的Excel，加几行/删几行数据，同时不破坏原有的格式和公式"。运营团队的日常报表**普遍带有自己的样式习惯**（字体、底纹、边框、数字格式），也**普遍包含公式**（不是偏门场景，是常态）。目标是让"增删行"这个最基础的操作，体验上接近用户自己在Excel里手动增删行的效果，而不是"生成一份新文件,丢了格式和公式"。

## 二、现状能力基线（已有的，不用重做）

- 已有一个安全的"从零生成"Excel引擎（`portable-xlsx-candidate.cjs`）：纯JS/fflate实现，输入纯数据（string/number/boolean/null），**明确设计为永不生成公式、宏、外链**，有完善的前置限额校验（Reject-before-Scan）和`degradations`字段用于报告"哪些内容没能保留"。
- 已有现成的Office文档读取/反读工具（`office-document-parser.cjs`、`office-zip-guard.cjs`、`ooxml-structured-text.cjs`），目前只读数据值，不读样式/公式结构。

## 三、本次要达成的核心需求

### 需求1：增删行
用户可以对一份已上传的Excel，提出"在第N行插入一行/删除第N行"这类请求，系统生成更新后的版本。新插入行的样式（见需求2）继承自**上一行**（已确认的产品决定）。

### 需求2：保留基本格式
以下这些需要在增删行操作后保留：字体（粗体/斜体/颜色）、单元格底纹、边框、数字格式（百分比/货币/日期显示）、列宽、行高。这些是静态展示信息，不涉及计算/执行，风险可控，预期是可以做到的，不是本文档要重点讨论的难点。

### 需求3：保留公式，并在增删行时正确调整引用 ——【这是需要重点评估的部分】

**期望的目标行为**：跟真实Excel的原生行为对齐——
- 公式里引用到行号**大于**插入/删除点的单元格/区域，行号应该自动+1（插入时）或-1（删除时），不管是相对引用还是绝对引用（真实Excel对insert/delete行时，相对和绝对引用的调整方式是一样的，$符号不影响这个场景下的调整）。
- 公式直接引用的单元格/行本身被删除：真实Excel会把该引用变成`#REF!`，这是预期中的正常结果，不是bug。
- 公式本身不涉及被修改行范围的，原样保留，不做任何改动。

**已知的、即便是真实Excel也处理不了的情况（不算新缺陷，照实承接即可）**：
- `INDIRECT()`、`OFFSET()`等通过字符串/动态方式构造引用的公式，无法被静态分析调整——这是公式本身的设计限制，真实Excel同样做不到自动调整这类公式，不需要为此专门开发。
- 跨工作簿引用（引用其他独立Excel文件）——如果当前产品本身不支持多文件关联，这类引用可以明确不处理。

**需要技术方案给出建议、而不是预设答案的开放问题**：

1. **当某个公式的引用范围跟本次增删的行有重叠，但系统暂时无法保证调整结果绝对正确时，应该怎么处理？** 我们之前讨论过"直接拒绝整次操作"，但这个方案被否决了——对运营日常使用者来说，"因为某个角落有个公式，我连加一行都做不了"会被当成产品缺陷而不是合理限制。希望这份需求能探讨更好的候选方向，包括但不限于：
   - 只精确标记/隔离"受影响的那几个具体单元格"（用`#REF!`或等价的明确提示），而不影响这次操作里其他不相关的行/单元格——即与真实Excel同样的局部降级行为，而不是整体拒绝；
   - 操作前先给用户一个"受影响范围预览"，用户确认后再执行；
   - 其他更优的技术方案。

   **目标是：这个体验不能比真实Excel本身的行为更差，也不能因为局部公式问题就拒绝整个基础操作。**

2. **是否需要支持命名范围（Named Range）、跨表引用（Sheet2!A1）、数组公式、Excel表格结构化引用（如`Table1[列名]`）？** 这几项的复杂度和优先级需要评估后再决定是否纳入第一版，还是可以先收窄到"同表内的普通单元格/区域引用"。

3. **公式解析本身打算怎么做？** 是否有现成的、经过验证的公式token解析/引用调整算法可以复用（哪怕是别的语言/库的实现思路），还是需要从零写一个最小化的公式引用调整器？这部分希望评估给出具体的技术路径建议。

## 四、明确排除（本次不要求，但如果评估后发现能以很低成本顺带做到，可以额外说明）

- 合并单元格
- 条件格式规则
- 嵌入图片/Logo
- 图表
- 透视表

这几项已经跟产品侧确认过排除在第一版之外，排除理由是：即便在成熟的专用库里，这几项的可靠往返处理也是出错率最高、最容易悄悄破坏文件的部分。**但如果技术评估认为某一项成本很低、风险可控，欢迎单独指出，不是说这几项完全不能讨论，只是不强制要求。**

## 五、验证方式建议

比照现有`portable-xlsx-candidate`的验证模式：多组真实fixture（带公式、带格式的Excel样本）→ 执行增删行操作 → 用现有反读工具校验结果 → 对比预期的格式/公式/引用调整是否正确 → 明确记录哪些情况触发了`degradations`或局部降级提示。

## 六、技术方案评估进展与下一步验证任务（给Codex，修正版）

### 6.1 先纠正：上一轮调研偏离了原始要求的两个地方

这不是口味问题，是直接违反了当时下给调研任务（《工具生态调研需求-给外部AI研究-20261105.md》）里写明的边界，必须先纠正，否则后面的判断会建立在错的地基上。

**偏差 1：重新论证了"DSH 原生有没有这些能力"，而且论证结论与已有审计结论相反。**

原始调研任务书写的是："不需要重新论证'DSH原生有没有这些能力'——已经审计确认DSH内核本身没有，这是已知事实，不用重复验证。"但上一轮调研报告的核心论点恰恰是"DSH 官方已经提供 Office Skills、浏览器控制接口……不需要 PT 从零开发"，并把"确认 DSH 官方 Office Skill 覆盖范围"列为 P0——这既是在重新论证一个被明确要求不要再论证的问题，论证出的结论还跟团队已有审计结论相反。

核实结果：**团队原来的审计结论是对的，上一轮报告这部分结论是错的。**证据：

- 官方仓库 `deepseek-ai/deepseek-harness` 的 `packages/skill/` 目录下没有报告里给的那个路径（`packages/skill/skill-office`）。
- 官方仓库里有一条现存的 [GitHub Discussion #678](https://github.com/deepseek-ai/deepseek-harness/discussions/678)，标题是"建议支持 Office 全家桶文件类型（Word/Excel/PowerPoint）"——这是**社区在请求官方加这个能力**，直接说明官方现在没有，跟"已经提供、只需确认覆盖范围"是相反的结论。
- 围绕"dsh-office"这个名字，能搜到一长串第三方账号发的几乎同名同描述的仓库（[wwumit/dsh-office](https://github.com/wwumit/dsh-office)、Mikuzjc/dsh-office-for-mso、kw78/dsh-office-tools、Qithird/deepseek-harness-office、svkoh/dsh-ms-office、copylee711/dsh-office、omdsh-dev/dsh-office、Zhouenze130923/dsh-office-boost 等）——这些全是社区个人项目，不是官方的，而且普遍只有个位数 commit。

同样的模式在"浏览器自动化是 DSH 原生能力"这条结论上也重现了：报告推荐的 `xu1132/dsh-plugin-browser` 直接打开核实过，**1 个 star、0 个 fork、总共 1 次 commit，README 里的安装命令还留着没改的占位符 `github:you/dsh-plugin-browser`**——这是个没写完的模板，不是经过验证的"DSH 原生浏览器插件"。

DSH 的核心骨架（调度 `dsh-schedule`、任务 `dsh-tool-jobs`、工作流 `dsh-tool-workflow`、子Agent `dsh-tool-subagent`、MCP 接入 `dsh-mcp-client`、文件工具 `dsh-tool-fs`）确实是官方真实自带的——这部分是直接解包北极星自己 vendor 的 `@deepseek-ai/dsh-0.1.1-rc.2.tgz`，从它的 `package.json` 依赖列表里核对出来的，不是看报告转述，可以放心复用。但"Office 能力"和"浏览器自动化"这两项，官方层面确认没有，只有一个质量参差、大量单 commit 占位仓库组成的第三方插件生态——这跟原来的审计结论一致，请把这一条改回去，不要再往"DSH 已经覆盖"的方向推。

**偏差 2：完全没有回答"多租户隔离模型"这个必答项。**

原始调研任务书写得很明确："任何新接入的工具/插件，不管来源是开源还是商业，都必须先回答'它的隔离模型是什么、能不能证明不同用户之间不会互相访问到对方的数据'，这个问题没有令人满意的答案之前，这个工具不会被信任启用。请把这条作为评估每个候选方案时的必答项，不是可选项。"上一轮报告列出的每个候选项目（Excel MCP Server、DBHub、Playwright MCP、Firecrawl 等）**全部没有回答这个问题**——这是必答项被整体跳过，不是遗漏某一项的细节。

这一点在下面的 Excel MCP Server 候选上尤其关键：它是一个按文件路径读写 xlsx 的 Python MCP Server，如果以单进程常驻的方式跑在北极星这种多租户架构里，"会不会因为路径参数、并发请求之间的状态混用，导致租户 A 的 Agent 会话碰到租户 B 正在编辑的文件"这件事必须先有答案，再谈公式引用调不调得对。这跟北极星之前关掉 DSH 原生文件/命令工具的理由（"cwd 不是真正的多租户沙箱"）是同一类风险，不能因为换了一个具体项目名字就不问了。

### 6.3 接下来真正要做的事（给 Codex 的具体任务）

**本轮只做验证和测试，不接入生产环境，不替换、不修改现有的 `portable-xlsx-candidate.cjs` 引擎。**

**任务 A（前置，必须先做，不能跳）：回答 Excel MCP Server 的多租户隔离问题**

针对 `haris-musa/excel-mcp-server`，具体回答：

1. 它是无状态的（每次请求独立进程/独立上下文），还是常驻进程+内存状态（如果是后者，并发的多租户请求之间有没有状态串用的可能）？
2. 它接受的文件路径参数有没有做任何沙箱限制？如果直接把它跑在北极星现有的每租户常驻 DSH 进程里，能不能保证它只能摸到当前租户工作区里的文件，摸不到别的租户的？
3. 如果用 stdio 模式接入（每次任务起一个子进程），这个开销和现有 DSH 子进程调度模型是否冲突/能否兼容？

这个问题没有清楚答案之前，不要往下做任何"好不好用"的功能测试——这是强制顺序，不是建议。

**任务 B：拿真实 fixture 测本文档第三节里悬而未决的核心问题**

用至少 5~8 份真实、带公式带格式的 xlsx 样本（可以用团队内部真实报表脱敏，或自己构造覆盖以下场景），测试 Excel MCP Server 对"增删行"的实际处理：

- 普通相对引用（`=A5`）和绝对引用（`=$A$5`）在插入/删除点之后的行，调整方式是否跟真实 Excel 一致（这是 release note 完全没提到的细节，必须自己测，不能信 README）。
- 跨工作表引用（`Sheet2!A1`）在源表或目标表发生增删行时是否正确跟随。
- 公式直接引用被删除的行/单元格，是否正确变成 `#REF!`，而不是报错中断或静默算出错误结果。
- **重点**：当测试触发"公式引用与改动行有重叠、无法保证调整绝对正确"这类场景时，Excel MCP Server 实际的处理方式是什么——是精确标记受影响的单元格（局部降级，符合本文档第三节的期望方向），还是像它在透视表场景里那样"整个操作失败、不保存任何改动"（这跟本文档里已经被否决的"直接拒绝整次操作"是同一类策略，如果 Excel MCP Server 在公式这件事上也是走这条路，说明它没有解决本需求里最核心的那个问题，需要明确指出，不要因为"它有安全机制"就当成满足需求）。
- 命名范围（Named Range）在增删行后是否正确调整。
- 合并单元格、条件格式在增删行后的实际表现（排除项，但既然顺手能测，记录下来供参考）。
- License 原文核实：去仓库的 `LICENSE` 文件里确认具体协议（有说法称是 MIT，但来源不是官方发布说明，需要拿仓库原文核实一遍，确认可商用）。

**任务 C：如果 Excel MCP Server 在任务 B 里暴露出明显短板**

不要就此判定"没有现成方案、必须自研"，而是按第五节同一套验证流程，再对照测一轮 Apache POI（Java，社区最成熟的 OOXML 库）和 LibreOffice UNO（命令行转换/脚本操作），确认是否有更可靠的候选，并给出各自的接入成本对比（语言栈是否跟北极星现有 Node.js 后端兼容、是否需要额外起进程/服务）。
