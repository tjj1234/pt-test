# 网页信息提取 × Firecrawl 验证任务书（给 Codex）

> 定位：P1。Firecrawl 是真实的独立公司/项目（有开源自托管版和云服务版），这项不需要先纠正事实前提。但跟"浏览器自动化"那份任务书有场景重叠，先看第一节再决定要不要做。

## 一、先确认这项跟浏览器自动化任务是不是重复

Firecrawl 做的是"把网页内容抓取/转换成结构化文本/Markdown"，跟《浏览器自动化-PlaywrightMCP验证任务书》里"点击/输入/交互式操作网页"是两类不同的事——前者是"看页面内容"，后者是"操作页面"。如果运营团队的真实需求是"收集某个竞品官网/落地页的文案内容"，Firecrawl 更合适；如果是"登录后台点点点、填表、翻页操作"，是 Playwright MCP 的事。

**请先跟产品确认实际使用场景是哪一种，避免两个任务书都做一遍类似的浏览器相关验证，浪费重复工作量。** 如果场景明确只需要"读内容"，这项任务可以独立往下做；如果需要"操作+读内容"两者都要，评估能不能先只做 Playwright MCP 一条路径覆盖，不必同时接两套工具。

## 二、现状基线

北极星当前没有任何网页抓取/内容提取能力。这跟浏览器自动化一样，属于《工具生态调研需求》里"方向2/3"的储备性调研范围，不是紧急需求。

## 三、前置必答题

1. 自托管版 vs 云服务版：用云服务版意味着把要抓取的网页 URL、甚至页面返回内容经过 Firecrawl 自己的服务器——这对多租户数据边界有没有影响，需要明确说清楚；自托管版的部署/运维成本是什么。
2. 多租户隔离：不同租户的抓取任务之间有没有串用风险（比如并发请求、速率限制是否按租户区分）？
3. 它抓取的网页内容如果包含恶意注入文本（比如一个网页故意写了"忽略之前指令"之类的话），后续流程有没有把这当成不可信数据处理的机制，还是会直接拼进模型上下文？

## 四、功能验证任务

1. 用运营团队真实会抓取的场景（比如某个竞品落地页、某个投放渠道的公开说明页）测试抓取效果和转 Markdown 的质量。
2. License 原文核实（开源自托管版和云服务版可能是不同条款，两个都要核实清楚）。
3. 核实接入现有 DSH MCP 客户端的实际工作量。

## 五、边界

- 本轮只做调研储备，不是紧急任务，不用赶进度。
- 不要在没搞清楚"读内容"和"操作页面"是不是同一个需求之前，就同时推进这项和浏览器自动化那项。

## 六、交付物

Markdown 报告：场景重叠确认结果 + 自托管/云服务的数据边界评估 + 隔离回答 + 抓取质量实测 + License 核实 + 是否建议引入。
