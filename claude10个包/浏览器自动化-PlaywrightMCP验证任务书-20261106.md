# 浏览器自动化 × Playwright MCP 验证任务书（给 Codex）

> 定位：上一轮报告把"DSH Browser-use + Playwright"打包成一项，推荐"官方 Playwright MCP 和原生 `dsh-plugin-browser` 二选一"。核实下来，`dsh-plugin-browser`（xu1132 发布的那个）不是经过验证的"DSH 原生插件"——直接打开仓库核实过，1 个 star、0 个 fork、总共 1 次 commit，README 安装命令还留着没改的占位符 `github:you/dsh-plugin-browser`，是个没写完的模板，跟"DSH 官方/原生"完全不是一回事。**这不是一个五五开的选择，直接只走 Playwright MCP 这一条路，`dsh-plugin-browser` 不用再考虑。**

## 一、现状基线

北极星当前没有任何浏览器自动化能力。这件事在最初给外部研究者的调研任务书里就写清楚过："方向2：浏览器自动化……目前还没排期，先做调研储备"——属于储备性调研，不是紧急需求，优先级按这个定位来，不要因为上一轮报告把它标成 P0 就当成紧急任务。

## 二、候选：微软官方 `playwright-mcp`

官方维护、MIT 协议、可自托管。

## 三、前置必答题（原始调研任务书里对浏览器自动化这个方向本来就点名要问的，直接照做）

1. 它是如何做"用户授权范围控制"的——能不能限制成"只能操作某个明确指定的窗口/标签页"，而不是无限制控制整台浏览器？
2. 它的动作是结构化 schema（点击/输入/滚动有明确参数），还是依赖视觉模型自己判断坐标？两种方式在准确率和出错时的可控性上分别怎么样？
3. 是否有先例显示它被用在多租户/企业内部产品里，并通过了安全审查？
4. 多租户隔离的必答项（跟其他候选一样）：如果北极星的每租户常驻会话都能调用这个浏览器工具，怎么保证租户 A 的 Agent 不会意外操作到租户 B 相关的浏览器会话/cookie/登录态？浏览器本身是否按租户隔离起独立实例，还是共享一个浏览器进程？

## 四、功能验证任务（前置问题答完才做）

1. 找一个北极星运营场景里真实会用到的网页操作例子（比如"打开某个广告平台的后台页面，读一下某个指标"），测试结构化动作的可靠性和失败时的表现（页面结构变化、元素找不到时会不会乱点）。
2. 核实接入 DSH 现有 MCP 客户端（`dsh-mcp-client`，这是真实存在的 DSH 原生能力）的实际工作量。
3. License 原文核实，确认可商用。
