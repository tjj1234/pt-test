# 复杂文档理解 × Docling 验证任务书（给 Codex）

> 定位：P1。Docling（IBM/Linux Foundation AI 项目）是真实、有正式背书的开源项目，这项不需要先纠正事实前提，可以直接进入验证。

## 一、现状基线（不用重新调研，避免重复造轮子）

北极星已经有现成的文档读取工具：`office-document-parser.cjs`、`office-zip-guard.cjs`、`ooxml-structured-text.cjs`——**目前只读数据值，不读样式/公式结构**（这是 Excel 原地编辑那份需求文档里写明的基线）。另外，包02（文档解析/OCR）已经由 Gemini 完成，覆盖了基础的 PDF/OCR 解析。

这项任务要回答的核心问题是：**Docling 比现有这套基础能力，到底多出来多少？**——不是"有没有文档解析能力"（已经有），是"复杂表格/版式结构还原"这一层现有工具做不到的事，Docling 能不能补上。

## 二、前置必答题

1. Docling 是本地跑的库（Python），还是需要起独立服务？如果是常驻服务，怎么隔离不同租户同时在处理的文档，避免一个租户的解析任务读到另一个租户上传的文件？
2. 它处理用户上传的文档时，是否有任何数据外传的环节（比如调用云端 API 做某一步解析），还是完全本地处理？这对多租户数据边界很关键，必须明确回答。

## 三、功能验证任务

1. 用北极星实际场景里会遇到的复杂文档样本（比如带合并单元格的广告花费报表 PDF、多栏版式的报告）对比测试：现有 `office-document-parser.cjs` 系列工具的解析结果 vs Docling 的解析结果，具体说清楚 Docling 在哪些 case 上明显更好、好在哪（表格结构保留？阅读顺序还原？）。
2. 接入成本评估：Python 库跟北极星现有 Node.js 后端（`shell/`）怎么对接——是起一个独立 Python 微服务，还是走 MCP 协议封装，各自的运维/部署成本说清楚。
3. License 原文核实，确认可商用。

## 四、边界

- 不需要重新验证"要不要自己写文档解析"——现有基础能力已经有了，这项只评估 Docling 补充的增量价值。
- 本轮只做对比测试，不替换现有的 `office-document-parser.cjs` 系列工具。
