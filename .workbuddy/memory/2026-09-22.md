## collect 接口 503 QUEUE_UNAVAILABLE 排查与修复验证

**现象**：`POST /api/v1/collect/wh_powertokens_001` 返回 503 + `{"ok":false,"error":{"code":"QUEUE_UNAVAILABLE"}}`；请求体/Secret 本身没问题（否则会先 400/401/403）。

**根因**（两层，均在代码层）：
1. `attribution_raw_events` 表从未被建。`createSqlPersistence` 的 `ensureSchema()` 会建表，但从未被调用；迁移脚本（001/002/003 + 003_delivery）也没建它。enqueue 里 `insertRawEvent` 一写就抛 `relation does not exist` → 被 server.js 吞成 503。
2. 该表在 `a2_raw_dlq.sql` 里带 `FORCE ROW LEVEL SECURITY`，而连接角色是 `pt_app`（非超级用户、RLS 生效）。enqueue 的 INSERT 没设 `app.current_tenant_id`，WITH CHECK 会拦掉写入。

**修复（用户已完成并验证）**：
- 建表挪到 `analytics/lib/db.cjs` 的超级用户迁移阶段：迁移列表新增 `a2_raw_dlq.sql`（排在 003_delivery.sql 之后，因依赖 pt_app 角色先存在）。`backend/collect/deps.cjs` 的 `wrapCollectQueue` 明确不再运行时 `ensureSchema()`（pt_app 无 CREATE 权限，运行时建表必失败）。
- `business/attribution/persistence/sql.js` 新增 `withTenant(pool, tenantId, fn)` 辅助函数（事务内 `set_config('app.current_tenant_id', …, true)`），`insertRawEvent / insertDlq / listDlq / getRawEvent` 全部包进 `withTenant` 满足 RLS。

**验证**：本沙箱用独立临时数据目录 + 端口 8096 拉起 `node start.cjs`，启动日志显示 `迁移 a2_raw_dlq.sql 执行成功`、`角色 pt_app 非超级用户/不绕过RLS`，POST collect 实测返回 **HTTP 200 + ok:true**。两处修复干净环境下完整跑通。

**注意（运维层，非代码）**：用户真实部署的 8095 当时返回 502（`upstream connect failed: 目标计算机积极拒绝`），即 8095 前面的代理连不上后端上游 = 后端进程没在跑。代码已对，需用户重启 8095 后端使新迁移生效。

## 用户说"你重启把" → 我实际重启 8095 后端并修两处运维级坑

**环境事实**：WorkBuddy 沙箱与宿主机（DESKTOP-27ASJOB）是同一台机器、同一 TCP 栈（PowerShell `Get-NetTCPConnection -LocalPort 8095` 能看到我起的实例 PID 5280）。所以我从沙箱 `node start.cjs` 起的 8095 实例，用户本机 `127.0.0.1:8095` 的 curl 能直接连上。`.pgdata` 是同一份文件，不是分离环境（早先漏斗查到 10777 事件、此后重启 seed 又写了 10777，数据一致）。

**重启中暴露并修复的两个阻断点**：
1. **迁移非幂等**：`analytics/backend/db/001_init.sql` 第 168 行 `CREATE POLICY tenant_isolation ON pt_events` 没有 `IF NOT EXISTS` / `DROP POLICY IF EXISTS`。迁移每次启动都整段重跑（db.cjs 无"已迁移"记录表），首次跑通后重启就撞 `policy already exists` 直接崩溃。已改为 `DROP POLICY IF EXISTS ...; CREATE POLICY ...`（与 a2_raw_dlq.sql 风格一致）。其余 002/003/003_delivery/a2 本就幂等，无需改。
2. **webhook 端点缺失 → 403**：`start.cjs` 在"已有事件>0"时跳过 seed，而 `webhook_endpoints` 表的 `wh_powertokens_001` 记录靠 `seed.cjs` 写入。`.pgdata` 是旧 seed 时期建的（没有该端点行），重启后 collect 查不到端点 → 403 `INVALID_SECRET`。（注：用户"改完代码"很可能把 webhook 鉴权从比对环境变量改成查 `webhook_endpoints` 表，旧数据目录没这条记录。）用一次性脚本 upsert 了该端点（secret_hash=sha256(b376a835...)=7263ea80...，与库内完全一致，证明记录本是对的，只是缺这一行）。

**最终结果**：8095 实例在宿主机跑起来（PID 5280），启动日志六项自检全绿、`a2_raw_dlq.sql` 迁移成功、seed 完成；用用户原始 curl 实测 `POST /api/v1/collect/wh_powertokens_001` → **HTTP 200 `{"ok":true,...}`**。502/503/403 全部消除。

**注意**：本次重启 seed 重新跑了一次（启动日志"灌数据完成"），数据是确定性 demo seed（10777 事件）。若用户原 8095 用的是非默认 `PT_DASH_DATA_DIR`，需确认我起的实例数据目录是否一致。后续若再次重启 8095，命令：`PT_DASH_PORT=8095 PT_DASH_TOKEN=<读 .env> PT_DASH_WEBHOOK_SECRET=<读 .env> PT_DASH_DATA_DIR=<analytics/.pgdata> node analytics/start.cjs`（token 从 `D:/trae001/pt-test/.env` 取，不可硬编码进记忆）。
